# T-577 — the check-width floor and the degenerate-framing null, measured

ADR-0022 §4.3 set `min_check_width = 8` as an **assumption**. The budget prices a *rate*, and §4.2 already turns any width into the frame count that meets it. What the budget cannot see is a **degenerate null**: a check satisfied by a framing artefact rather than by a code. This ticket measures that null per width and gives a verdict. It also answers the two questions T-575's `differences` swap depends on.

**Verdict: CHANGE THE FLOOR to 16 for the count that ships today.** 8 is a measured GO only together with the count change in §4 (`independent_frames`). Below 8 is never safe: the period artefact passes a 4-bit check with certainty, whatever the count. Two holes also survive **any** floor and are closed only by the count change: the init-cancel frame (worst at w = 32) and the searched shift artefact (at every width). The ADR's rule that numbers are "never loosened after seeing results" is respected: the measured floor is *higher* than the assumption.

## 1. Method

The harness is `crates/hk-estimate/tests/degenerate_null.rs`. By default it runs as an 11-second assertion suite that pins the findings. The numbers below come from the full run:

```
HK_T577_TRIALS=4000 HK_T577_SEARCH_TRIALS=100 \
  cargo nextest run -p hk-estimate -E 'binary(degenerate_null)' --no-capture
```

**Every input carries no code.** A width-*w* check that reaches the ADR-0022 §6 gate on such input is therefore a false confirm. The harness uses the real parts the gate reads, not re-implementations of them:

- `hk_estimate::framing::crc::BitCrc`: the `crc` block's engine.
- `hk_model::synth::null::check_bits`: the S5 `check_distinct_valid` binomial, including the `tested` multiplicity.
- `hk_model::synth::null::is_short_periodic`: the guard `CheckTally` applies.
- `hk_estimate::assist::search_codes`: the searched-generator path.

The gate is ADR-0022 §6 steps 1–3 in check-only accounting: `min(check_bits(d, tested, w), w·d) − L_check ≥ 24`, which subsumes the 16-bit hard floor. `L_check = 0` for a template and `w + 5` for a search.

**One window is one confirm decision.** Each window holds 24 frames of 96 bits, or 48 grid blocks.

**Templates.** One catalogue generator per width: CRC-4/ITU, CRC-8/SMBUS, CRC-12/DECT, CRC-16/XMODEM, CRC-24/Mode-S and CRC-32. Each is tested **linear** (init 0, as in Mode-S, XMODEM, KERMIT, ARC and SMBUS) and **affine** (init all-ones, as in CCITT-FALSE and CRC-32).

**Framers:**

- `anchored`: exact burst onset, like a preamble.
- `jitter≤7`: an energy gate with 0–7 bits of onset error.
- `grid`: fixed blocks, as in stream/block mode, or a framing search over a lattice. Bursts land at arbitrary phase.

| Population | Model |
|---|---|
| N1/N3 iid | 16-QAM / OFDM / thermal through a hard slicer: fair independent bits |
| N2 runs | CW, NBFM and AM voice through a discriminator slicer: long runs (stay p = 0.97) |
| N3 DSSS | a 127-chip m-sequence (x⁷+x³+1) over random data |
| A beacon | one no-code emitter repeating a 40-bit burst over idle zeros |
| A beacon \| g∣P | the same, conditioned on the one chance event g ∣ P (probability exactly 2⁻ʷ for a linear check). Importance sampling: rate = 2⁻ʷ × the measured figure |
| A sensor | no-code sensor: fixed 16-bit id, a 12-bit random-walk value, 12 fixed bits |
| A repeat | a random payload sent twice at lag ord(x mod g) (≤ 20 bits) |
| A Manchester | a 20-bit payload Manchester-coded, never decoded |

The budget per decision is 1/N = 5.0 × 10⁻⁵ = 2⁻¹⁴·²⁹ (ADR-0022 §1.2). The model's claim at the gate is 2⁻²⁴ = 6.0 × 10⁻⁸. Zero events in *n* windows are shown as the one-sided 95 % bound, < 3/*n*.

## 2. Measurement 1 — the degenerate null, per width

### 2.1 The N2/N3 populations: no degenerate tail except one

Template-fixed, 4000 windows per cell, every framer, linear and affine: **0 gate passes at every width**, a bound of < 7.5 × 10⁻⁴ per decision, with one exception, §2.3. The `tested` multiplicity inside `check_bits` is what holds. The per-frame pass rate shows where the per-frame independence assumption breaks. It does not break the gate:

| Population | w | frame pass rate | 2⁻ʷ | inflation |
|---|---|---|---|---|
| iid | 8 / 12 / 16 | 3.8e-3 / 2.1e-4 / 1.0e-5 | 3.9e-3 / 2.4e-4 / 1.5e-5 | ≈ 1× (the model holds) |
| N2 runs, linear | 8 / 12 / 16 | 3.0e-2 / 2.9e-2 / 2.8e-2 | — | 8× / 120× / 1 800× (idle-constant frames) |
| N3 DSSS, grid, linear | 8 | 5.2e-2 | 3.9e-3 | 13× (LFSR windows are linear-recurrent) |

A distinct-valid count with no short-period guard would have passed **44–48 %** of N2 windows at w = 24/32 (`dv>=req` column). It would also have passed **100 %** of idle grid windows, because the all-zero frame satisfies every linear check. The shipped `differences` guard takes both to 0. The guard does real work, and §3 relies on this.

Searched (`search_codes`, 12 frames, `L_check = w + 5`, 100 windows): N1/N3 iid, N2 runs and N3 DSSS give **0 claims reaching the gate at every width**, anchored and grid (< 3 × 10⁻²).

### 2.2 Degenerate null B, the shift artefact: sets a floor for the shipped count

For a **linear** check, g ∣ P implies g ∣ x^k·P, so every zero-padded shift of a chance-valid burst is valid. `CheckTally` hashes whole frames, so every shift is a new "difference". A framer that offers shifts of one burst therefore turns **one** 2⁻ʷ event into many credited frames. Onset jitter does this, a block grid does it, and so does a framing search over offsets. Seeded (conditional on g ∣ P):

| framer | w = 4 | 8 | 12 | 16 | 24 | 32 |
|---|---|---|---|---|---|---|
| jitter≤7, shipped gate | 0 | **0.999** | **1.00** | **1.00** | **1.00** | 0.997 † |
| grid, shipped gate | 0.454 | **1.00** | **1.00** | **1.00** | **1.00** | 0.997 † |
| either, with the rank cap | same | same | same | same | same | same |
| either, **proposed count (§4)** | 0 | **0** | **0** | **0** | ≤ 5e-4 | 0.997 † |

† A single CRC-32 frame carries about 28 bits after the `tested` charge. That is the designed single-burst confirm (ADR-0022 §4.2), and its rate, 2⁻³², is what the model claims.

So the **per-decision false-confirm rate is 2⁻ʷ, not 2⁻²⁴**. Direct (unseeded) measurement agrees: beacon/grid gives 2.5 × 10⁻² at w = 4, 3.0 × 10⁻³ at w = 8 and 2.5 × 10⁻⁴ at w = 12; beacon/jitter gives 4.0 × 10⁻³ at w = 8. A no-code **sensor** does the same: 1.5–2.3 × 10⁻³ at w = 8 and 2.5–7.5 × 10⁻⁴ at w = 12. Against the budget:

| w | shift-artefact rate per decision | vs budget 5.0e-5 | vs model margin M = 2⁹·⁷ over 2⁻²⁴ |
|---|---|---|---|
| 4 | 6.2e-2 | 1 250× over | — |
| 8 | 3.9e-3 (measured 3.0–4.0e-3) | **78× over** | breaks it by 2⁶·³ |
| 12 | 2.4e-4 (measured 2.5e-4) | **4.9× over** | breaks it by 2²·³ |
| **16** | **1.5e-5** | **0.31×, inside** | inside (2⁸ ≤ 2⁹·⁷) |
| 24 | 6.0e-8 | inside | inside |

That is the floor for the count that ships: **16**, the smallest template width at which a no-code burst framed with shifts stays inside the budget. It stays inside only with 1.7 bits of the 9.7-bit margin left; the rest is spent. This is the "below about a byte" worry of ADR-0022 §4.3, measured: the edge is two bytes, not one. An exact anchor, or an affine check, closes the door (anchored/linear: 0 at w = 8/12; affine: 0 everywhere). The shipped path cannot assume either.

The **GF(2) rank cap does not fix it**: shifted copies are linearly independent (`gate|rank` column). **The proposed count does**: it counts a frame whose zero-trimmed polynomial is a multiple of one already counted as no new trial, since m·P is valid by construction once P is. It reads 0 of 4000 at w = 8, 12 and 16 in every seeded cell.

### 2.3 Degenerate null A, init-cancel: floor-independent, and worst at the top

An **affine** check with init = all ones is satisfied by `1^w ‖ 0…0`: the first *w* bits cancel the register and the rest is idle. With xorout ≠ 0 the degenerate frame is `init ‖ 0…0 ‖ xorout`. Neither frame is periodic as a whole, so `is_short_periodic` passes it and `differences` counts it. A CW or voice slicer emits it whenever its single transition lands on bit *w*. One such frame is enough once the width alone covers the 24 bits:

| N2 runs, affine | w = 24 | w = 32 |
|---|---|---|
| shipped gate | 0 (the `tested` charge holds) | **2.0–2.3 × 10⁻² per decision, 400× over budget** |
| proposed count | 0 | **0** |

**No floor fixes this; a higher floor makes it worse.** The fix is the guard applied with up to *w* bits trimmed from either end (`degenerate_frame`). The test pins the frame deterministically at every width.

### 2.4 Degenerate null C, the period artefact: the reason for "not below a byte"

A payload repeated at lag ord(x mod g) satisfies the check **whatever the payload**, because x^L ≡ 1. ord ≤ 2^w − 1, so for w = 4 the lag is at most 15 bits (CRC-4/ITU: 15). A 15-bit code sent twice satisfies a 4-bit check on every frame, and every frame is distinct:

- **w = 4: gate rate 1.00 anchored, 0.975 grid; 0.9985 / 0.944 even with the proposed count.** Nothing in the counting can remove it, because the frames really are independent payloads.
- For w ≥ 8 the catalogue generators have orders above the frame, and the rate is 0. This is not a law: a byte-wide generator with a small-order factor exists. It is the reason the floor sits at a byte and not at 4.

### 2.5 Searched: the shift artefact at every width

`search_codes` on no-code beacon frames, grid framing. The GCD of shifted copies contains the burst polynomial, so any degree-*w* divisor of P fits every frame:

| searched, beacon/grid, 100 windows | w = 4 | 8 | 12 | 16 | 24 | 32 |
|---|---|---|---|---|---|---|
| unseeded, shipped gate | 8e-2 | 1e-2 | 0 | 0 | 3e-2 | **1.5e-1** |
| seeded, shipped gate | 0.20 | 0.21 | 0 | 0.25 | 0.29 | 0.31 |
| unseeded and seeded, **proposed count upstream** (only `independent_frames` reach the search) | **0** | **0** | **0** | **0** | **0** | **0** |

The rate does **not** fall with width; it rises at w = 32. **ADR-0021 §8.2's null control is not built to see this.** A time-reversed window holds P*, which g does not divide, and a phase-randomised surrogate destroys the bursts, so the null windows score low and the margin passes. This is reasoned, not run: the harness does not drive the engine. The repeat source passes searched at w = 8/12/16, at 0.19 / 0.23 / 0.25 on grid, and still at 0.26 / 0.35 / 0.47 with the proposed count. That is expected: it is real redundancy, a repetition code whose generator 1 + x^L the fitted g divides. It is not a shift artefact, and no count should remove it. Whether a repetition code may *confirm* is a separate question for §2.4 and the null control.

## 3. Measurement 2 — `distinct_valid` versus `differences` on real emitters

Emitters **with** a code, template-fixed, anchored, mean over 200 runs. T-575's swap assumed these two counts differ on repeated-payload emitters; the measurement found a gap of zero:

| emitter (w) | k | repeat count | distinct_valid | differences | gap |
|---|---|---|---|---|---|
| beacon, fixed payload (16) | 64 | 64 | 1 | 1 | **0** |
| two-message toggle (16) | 64 | 64 | 2 | 2 | **0** |
| sensor, 3× repeats (8) | 128 | 128 | 17.3 | 17.3 | **0** |
| rolling counter (16) | 128 | 128 | 128 | 128 | **0** |
| DF17-like squitter (24) | 128 | 128 | 128 | 128 | **0** |

**The gap is 0.0 at every k on every emitter.** `CheckSummary::distinct_valid` is already de-duplicated, so the two differ only by short-periodic frames, and a real emitter sends none. What over-credits a beacon is the **repeat count** (64 against 1), which neither field uses. **The swap costs a real emitter nothing.** Its value is entirely on the null side (§2.1): the short-period guard takes N2 at w = 24/32 from 44–48 % to 0, and idle grid windows from 100 % to 0. So the old rule over-credited by "the idle frames", not by "the repeats". `assist::codes`' D reads one lower (7.0 at k = 8 for the counter): that is the one constant per group the search pays, and `L_check`'s *w* charges it again. The proposed count (`indep` column) equals `differences` on every real emitter at every k.

## 4. Measurement 3 — `max_countable_differences`: independence saturates at the rank, not at a frame count

For a linear (or affine, same-length) check, a frame in the GF(2) span of the counted frames' differences is **valid automatically** once they are. The number of independent trials is therefore the **affine rank + 1** of the valid frames:

| emitter | varying payload bits | differences at k = 128 | rank + 1 at k = 128 | saturates at |
|---|---|---|---|---|
| sensor (slow walk, 20 bits nominally varying) | 20 | 17.3 | **7.4** | ~7 by k ≈ 64: only the low bits ever move |
| rolling counter | 16 | 128 | **9.0** | log₂(k) + 2: the counter's low bits |
| DF17-like squitter | 40 (ME) | 128 | **41** | 41 at k ≥ 64: the payload's dimension |
| beacon / toggle | 0 / 1 | 1 / 2 | 1 / 2 | immediately |

So **`max_countable_differences` is the affine rank + 1, a per-job quantity, not a constant.** The chance-factor confidence in `assist::codes` saturates near 8 frames. Independence happens to saturate there for the slow sensor, but not for a counter (it grows with log k) and not for a squitter (it grows until 41). Independence therefore saturates in a different place, and a constant cap would be wrong both ways.

For bits the direction matters: `differences` over-counts a counter 14× and a slow sensor 2.3×. Those are real codes, where over-counting costs nothing. The null the gate guards is a no-code frame set, where rank-dependent frames are free passes. The rank cap costs one Gaussian elimination over ≤ 256 frames. It is necessary, but not sufficient: §2.2 shows it does not catch shifts.

## 5. What goes back where

- **ADR-0022 §4.3**, amended alongside this result: `min_check_width = 16` for the shipped count (measured, §2.2); 8 once the count is `min(independent_frames, affine_rank + 1)` with the trimmed degenerate guard (§§2.2–2.4, 4), re-measured by this harness; never below 8 (§2.4).
- **T-575** (the ConfirmPolicy it builds, and the constant already at `hk-pipeline` `inventory.rs` `min_check_width: 8` and `hk-synth` `engine.rs` `min_check_width: 8`): set 16, **or** land the count change and keep 8. The init-cancel guard (§2.3) is needed either way, because no floor closes it. The searched path (§2.5) needs the count change applied to the frames `search_codes` sees; the null control does not cover it.
- **What this does not measure.** It does not drive the full engine: the framings are modelled, and whether the engine's framers offer shifted copies is the empirical question that decides how often §2.2 actually fires. It also runs no real IQ; T-576's A2 over ADR-0021's populations is the end-to-end measurement. The 4000-window bounds (< 7.5 × 10⁻⁴) are far above the budget's 5 × 10⁻⁵, so a "0" row supports the claim only because each artefact also has a mechanism and a seeded rate. A zero on its own proves nothing.
